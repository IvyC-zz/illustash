## 2. 常驻核心进程

角色命令默认走一个常驻的 Rust 子进程，省掉每次命令的进程启动（`tests/reference/web/terms_core.py（#9 已删除）` 的 `character_command`）。

- Python 进程通过私有 stdin / stdout 管道持有子进程，不开端口。
- 宿主锁把请求串行化，Store 原来的写锁仍然有效；跨 Python 进程由 SQLite `BEGIN IMMEDIATE` 仲裁。
- 常驻入口与单次 CLI 共用同一套事务函数：一个命令一个事务，失败整事务回滚，名字同步、历史和后台事件仍在同一事务里。
- 每条命令独立打开并关闭 SQLite 连接，空闲时不占连接。
- 业务拒绝不重启进程；执行中崩溃，下一次调用时重启。
- 回退：环境变量 `ILLUSTASH_TERMS_DAEMON=0` 改回每次启动单次 CLI。

测试在 `tests/test_terms_service.py`。

## 3. 其他保留下来的做法

- 全量 refresh：核心先按原内容指纹预检 WD，只有真正变化的图继续走证据包路径；实体树与链接镜像的 UPSERT 值相同时不重复 UPDATE；全量归属在同一事务里只物化一次规则结果。
- 图片 NSFW 查询：需要总数的请求在同一读事务里物化一次筛选结果，再计数和分页；例外是只隐藏 NSFW、按日期排序且不带其他筛选的图库页（#48）：先用两次索引计数估算隐藏后剩下的比例，剩下至少 70% 且页面不超过前一半时，直接按 `assets_date` 索引分页、另行计数；NSFW 占多数或翻得更深时回到物化。阈值依据是 10k/50k 合成库按 NSFW 占比扫描的交叉点（约 40%），其余形状物化更快。同时筛标签与「仅 NSFW」时由 NSFW 投影驱动。没有持久缓存，没有跨请求复用。
- 角色命令的预演跳过末尾的派生表刷新，真正的刷新在核心里做。

## 4. 底线

以后再做性能优化，仍然是这几条：用户看得到的结果不变；对照零差异，比较器不放宽；对照基准（#201，`native/terms/tests/fixtures/baseline/`）不重录；不碰真实图库，要用就按「每步单独授权、只读一致性副本」的约定；回退一直可能。

## 5. 固定原生宿主基准

`tools/bench_native_contracts.sh /absolute/release/contracts-executable /absolute/main-host /absolute/candidate-host` 固定对两个显式 release 二进制交错运行各三次，分别取三次独立进程的中位数；测试入口用 `cargo test --release --locked --manifest-path native/terms/Cargo.toml --test contracts --no-run` 构建，debug 入口拒绝测量。main 二进制须从记录的远端 main 提交用 `cargo build --release --locked` 构建并单独保存，不能使用候选替代；脚本不读取用户包，全部输入由本仓库 HTTP 合成契约恢复至新临时目录。

数据集固定为 4,096 张合成资产、2 个参考角色：保留夹具中 3 图的证据与裁决，其余 4,093 图按固定编号/尺寸/日期加入 source 与应用表且未分类，不读取或解码图片。每轮只测原生宿主；启动、SQL 恢复/扩容不计延迟。浏览分页 `limit=100&offset=2000`、计数、单图详情各预热 5 次后测 50 次，标签加到 a/b 两图与撤销各测 20 次；每轮取平均请求时间（包含 loopback HTTP、JSON 解析及核心执行），最后取三轮平均值的中位数。内存为 `wait4` 返回的宿主整个生命周期峰值 RSS，macOS 以字节、Linux 以 KiB 转成 MiB（1,048,576 字节），不含测试进程；这是合成基础宿主口径，不覆盖大图库刷新、模型/worker 峰值或 Windows。

用户允许直接接受的门槛：候选内存增加严格小于 10 MiB，各项延迟退化严格小于 20%；脚本逐项打印 accepted/exceeds-threshold，超阈值以非零退出，零/负退化也接受。保持同数据、release、三次中位数，不以单次测量或 debug 数字替换。性能脚本不会更改任何契约期望或既有 golden。

2026-10-02，macOS arm64，实际 main `fc49031` release 对本变更候选 release，固定脚本各三次中位数：main 峰值 16.734 MiB，候选 16.813 MiB；浏览/计数/详情/标签/撤销的 main 基线分别 2.886/1.799/2.016/2.091/2.930 ms，候选分别 2.878/1.799/2.013/2.049/2.920 ms。最大延迟退化低于 +0.01%、内存增加 0.078 MiB，按上述用户阈值直接接受。基准仅回收本轮创建的宿主，wait4 回收后停止重复清理，不按端口查找或终止其他进程。该结果只说明此固定合成基础宿主样本，不代表四类契约的全部操作或整个 Python 行为网的性能。

## 6. 整应用识别吞吐基准

`tools/bench_recognition.py`（用法见文件开头）测一批新图从扫描到识别、导入完成的总时间、各阶段占比和峰值内存（#213 第 1 步）。之后改识别速度的 PR（包括 #213 第 2 步评估 CoreML / DirectML 执行后端）都用这份基准对比，按 [AGENTS.md](../AGENTS.md) 占 heavy 槽运行，写明负载和有没有虚拟机在跑。

**样本**：同一种子生成的 200 张合成图（8 种常见插画尺寸循环，750×1334 到 2480×3508，JPEG 与 PNG 混合，共 538 MP、207 MiB）和 2,000 个合成角色各一条随机锚点。不是真实图库，也不说明识别准确率。

**端到端**：重定位布局（与 `tests.platform_recognition_models` 相同）里启动 release 宿主，folder 来源新建图库后 `POST /api/sync`，每 50 ms 轮询到完成。宿主照常拉起 `illustash-recognition`，每 25 张一批，边识别边导入。不开名字、索引检查和研究任务，所以不含导入之后的相似计算等后台任务。线程数是产品默认值，CPU 执行后端：WD 在 Windows 上用 ONNX Runtime 默认值（每个物理核一个 intra-op 线程，2026-10-21 起，#213），macOS 用 4 个；CCIP 两边都用 ONNX Runtime 默认值。下表 2026-10-19 的数字是改之前测的，当时两边 WD 都是 4 个线程。图片文件已在系统缓存里。

**阶段分解**：`recognition-compute` 示例的 `bench-stages` 在一个进程里按 worker 的顺序处理同一批图并逐步计时。计时用的 WD 会话第一张图与生产 `ModelSessions` 逐位比对，配置变了基准就报错，不会悄悄测成别的东西。

- 解码：读文件并解码成 RGB。
- WD：预处理（缩放到 448）加推理。
- CCIP：预处理加推理。
- 检测与分级：WD 概率转标签和分级，加角色锚点认领。现在不另跑检测模型。
- 写结果包：每批的 npy、标签、sidecar 和完成标记。
- 写库：端到端里宿主在识别阶段用掉的 CPU 时间除以张数，包括导入校验、写 source / 应用库和投影。状态轮询的开销在同步完成后按同样频率空轮询量出来，已经扣掉。

worker 本身是串行的；导入在宿主进程里和下一批的识别同时进行，所以写库主要占 CPU，不直接加到墙钟上。占比按各阶段每张耗时之和计算。

**峰值内存**：每 20 ms 采样宿主和 worker 各自生命周期的峰值。macOS 是 `phys_footprint`（活动监视器「内存」一栏的口径），Windows 是 `PeakWorkingSetSize`。两边口径不同，不能直接比。

2026-10-19 的结果（Windows 在 `7a78509`、macOS 在 `501e475` 上测，两者之间只改了测量条件的记录；ONNX Runtime 1.30.0 CPU，两边模型文件相同；各 3 次中位数）：

| | macOS | Windows |
|---|---:|---:|
| 机器 | Apple M2 8 核、16 GB，macOS 26.7.1 arm64 | Intel 第 11 代 8 核 16 线程笔记本处理器、32 GB，Windows 11 x64 |
| 测量条件 | 开始时整机 CPU 占用 16%，没有虚拟机；本测量独占 heavy 槽，但其他会话的轻量工作没停（结束时 CPU 占用 40%）；前两次端到端用电池，之后接上电源，低电量模式关闭 | 整机 CPU 占用约 3%，没有虚拟机 |
| 端到端总时间（三次） | 345.3 s（461 / 345 / 332） | 224.4 s（225 / 220 / 224） |
| 每张平均 | 1,727 ms | 1,122 ms |
| 启动 worker 到第一张（含模型加载） | 3.9 s（模型加载约 3.2 s） | 3.6 s（约 2.0 s） |
| 收尾导入（最后一批识别完到同步完成） | 2.6 s | 1.1 s |
| 解码 | 20.5 ms（1.0%） | 23.5 ms（2.0%） |
| WD | 1,285 ms（63.7%） | 842 ms（71.0%） |

| 峰值内存：宿主 / worker | 187 / 1,111 MiB | 71 / 801 MiB |

两个平台上 WD 和 CCIP 两个模型的推理合计都占九成左右；解码、认领和写包加起来不到 3%。要提速，先看模型推理（执行后端、线程数），不是 I/O 或写库。写库主要和下一批的识别同时进行，墙钟上只多出最后一批的收尾导入。

这台 M2 比 Windows 机器慢：WD 每张多约 50%，CCIP 多到约 2.6 倍。第 1 步推测 CCIP 的默认线程数在 M2 上把能效核也算进去而吃亏；#213 第 2 步在空闲的 M2 上做了模型级对比，CCIP 限 4 线程和默认值一样快，WD 改 8 线程反而慢约 10%，推测不成立。同一次对比里，这台 M2 空闲时的 WD、CCIP 推理只有上表阶段耗时的一半左右，说明上表的 macOS 数字受了测量时负载的影响。

**Windows 的 WD 线程数（2026-10-21，#213 第 2 步）**：同一台 Windows 机器、同样 200 张合成图，在同一时段与 WD 4 线程交替各测 3 次，WD 8 线程（等于这台 8 核机器上的 ONNX Runtime 默认值）每张 897 ms（三次 897 / 905 / 897），4 线程 1,116 ms，快约 20%；WD 阶段 818 → 623 ms，worker 的 CPU 时间多约 30%。12 线程 830 ms、16 线程 920 ms（另测，16 线程和宿主导入抢核），没有采用。CPU 执行后端的输出与线程数无关，逐位相同，所以这个改动不影响识别结果、固定期望和 `tests.platform_recognition_models` 的逐位比对。执行后端（CoreML、DirectML）的评估结论见 [#213 的评论](https://github.com/shio-vinyl/illustash/issues/213)。

Windows 三次总时间相差不到 3%，阶段耗时相差不到 1%，可以直接拿来对比。macOS 三次的阶段耗时相差约 ±10%，第一次总时间明显偏高（开始时前一个 heavy 作业的余下负载还没退），所以 macOS 上比较改动前后时，要在同一时段交替测，差距小于 10% 不能下结论。每次 `GET /api/sync` 约花宿主 3 ms（Windows）到 6 ms（macOS）CPU。这些数字只适用于这组合成样本、这两台机器和 CPU 执行后端。
